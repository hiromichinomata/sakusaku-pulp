# 第14章　固定費と条件分岐をモデル化する

**初花**: うめ食品が新しい工場を作るんだって。釜を何個にするか、ラベル貼りの機械を入れるか、どの商品を作るか……決めることが山積みらしい。

**マリゴールド**: 今回の主役は **固定費** だよ。機械を入れたら、たくさん作っても少ししか作らなくても、毎月同じリース料がかかる。商品を作るなら、作る量に関係なく段取りの費用がかかる。

**初花**: 作る量に比例しない費用、ってことだね。第9章の利益の計算では、固定費は入れてなかった。

**マリゴールド**: そう、第9章で「固定費は第14章で」と予告したね。固定費は「やるか・やらないか」で発生するかどうかが決まるから、バイナリ変数と組み合わせて表すんだ。第12章の「数量と判断をつなぐ」書き方の応用編だよ。

---

## 14.1　生産設備を稼働させるかどうか

うめ食品の新工場の計画です（本書用の架空のデータです）。金額は円、数量はケース、期間は1か月です。

| 商品 | 1ケースの粗利 | 需要 | 釜を使う量（1ケースあたり） |
|------|-----------:|-----:|-----------------------:|
| ジャム | 1,500円 | 1,200 | 1.0 |
| シロップ | 1,200円 | 1,000 | 1.0 |
| ドレッシング | 900円 | 1,500 | 0.5 |

粗利は、価格から原材料費を引いた金額です。ここから、ラベル貼りの費用と固定費を引いたものを利益とします。

| 固定費・費用 | 金額 | 発生する条件 |
|------------|-----:|-----------|
| 段取り費 | 150,000円／月 | その商品を作るなら |
| 自動ラベラーのリース料 | 300,000円／月 | 自動ラベラーを入れるなら |
| 釜の固定費 | 下の表 | 選んだ釜の大きさによる |
| ラベル貼り（手作業） | 400円／ケース | 手で貼った分 |
| ラベル貼り（自動） | 100円／ケース | 自動ラベラーで貼った分 |

**初花**: 「その商品を作るなら」「入れるなら」——条件がいっぱい。

**マリゴールド**: 条件の数だけ、バイナリ変数を作るんだ。

```python
run = {p: prob.add_variable(f"run_{p}", cat="Binary") for p in products}   # その商品を作るか
size = {k: prob.add_variable(f"size_{k}", cat="Binary") for k in kettles}  # どの大きさの釜にするか
auto = prob.add_variable("auto", cat="Binary")                             # 自動ラベラーを入れるか
```

| 変数 | 1 の意味 | 0 の意味 |
|------|---------|---------|
| `run[p]` | 商品 p を作る（段取り費がかかる） | 作らない |
| `size[k]` | 釜 k を選ぶ（固定費がかかる） | 選ばない |
| `auto` | 自動ラベラーを入れる（リース料がかかる） | 入れない |

## 14.2　固定費と変動費を表現する

**マリゴールド**: 固定費は、**バイナリ変数 × 金額** で書ける。第11章で見た「掛け算のスイッチ」だね。

```python
fixed = (SETUP * pulp.lpSum(run.values())
         + pulp.lpSum(kettles[k]["fixed"] * size[k] for k in kettles)
         + AUTO_FIXED * auto)
```

**初花**: `run` が1の商品の数だけ段取り費がかかって、選んだ釜の固定費がかかって、自動ラベラーを入れたらリース料がかかる。

**マリゴールド**: そう。難しいのは、**固定費を払わないと、その設備は使えない** というつながりを書くところだよ。自動ラベラーで貼る量を `by_auto` という変数にして、こう書く。

```python
prob += pulp.lpSum(by_auto.values()) <= m * auto, "auto_link"   # 入れないなら自動では貼れない
```

| `auto` | 制約の意味 | ラベル貼りの費用 |
|--------|----------|--------------|
| 0（入れない） | `by_auto <= 0` → 全部手で貼る | 400円 × 全ケース |
| 1（入れる） | `by_auto <= m` → 自動で貼れる | 100円 × 自動の分 ＋ 30万円 |

**初花**: 第12章の `make <= 需要 × adopt` と同じ形だ。`m` は何を入れるの？

**マリゴールド**: 自動で貼る可能性のある最大の量、つまり全商品の需要の合計（3,700ケース）だよ。この `m` が Big-M で、14.5 で詳しく見る。

ラベル貼りの費用（変動費）は、手で貼った量と自動で貼った量に分けて計算します。

```python
label = pulp.lpSum(LABEL_HAND * (make[p] - by_auto[p]) + LABEL_AUTO * by_auto[p] for p in products)
```

```text
利益 ＝ 粗利 − ラベル貼りの費用（変動費） − 固定費
```

**初花**: 自動ラベラーは1ケースで300円節約できて、リース料が30万円。だから1,000ケース以上貼るなら入れたほうが得、ってことだね。

**マリゴールド**: その損益分岐の計算を、ソルバーがほかの判断と同時にやってくれるんだ。

## 14.3　最低生産量と最大生産量

**マリゴールド**: 商品を作るかどうかの `run` と、作る量の `make` も、第12章と同じ2本の制約でつなぐよ。

```python
prob += make[p] <= m * run[p], f"run_max_{p}"          # 作らないなら 0
prob += make[p] >= MIN_LOT * run[p], f"run_min_{p}"    # 作るなら最低ロット以上
```

```text
run = 0 → make = 0
run = 1 → 200 ≦ make ≦ 需要
```

**初花**: 「0か、200以上」っていう、飛び飛びの範囲になるんだね。

**マリゴールド**: こういう変数を **半連続変数** と呼ぶこともある。0は許すけど、作るならある程度まとまった量、という現場でよくある条件だよ。

| 条件 | 書き方 |
|------|-------|
| 作らないなら0 | `make <= M × run` |
| 作るなら最低量以上 | `make >= 最低量 × run` |
| 作るなら最大量まで | `make <= 最大量 × run`（M に最大量を使えば1本で済む） |

## 14.4　複数の選択肢から一つを選ぶ

**マリゴールド**: 釜の大きさは、三つの選択肢から一つを選ぶ。

| 釜 | 固定費（月） | 能力（釜を使う量／月） |
|----|----------:|------------------:|
| 小型釜 | 500,000円 | 1,200 |
| 中型釜 | 900,000円 | 2,000 |
| 大型釜 | 1,900,000円 | 3,000 |

**初花**: 「ちょうど一つ」なら、`size` の合計を1にすればいいね。第11章の「各作業にちょうど1人」と同じだ。

```python
prob += pulp.lpSum(size.values()) == 1, "one_kettle"
```

**マリゴールド**: そして、釜の能力は **選んだ釜の能力** になる。能力を `size` で重み付けして足せば、選ばれた1つだけが残るよ。

```python
prob += (pulp.lpSum(products[p]["kettle"] * make[p] for p in products)
         <= pulp.lpSum(kettles[k]["capacity"] * size[k] for k in kettles)), "kettle_capacity"
```

```text
中型釜を選んだとき： 1200 × 0 ＋ 2000 × 1 ＋ 3000 × 0 ＝ 2000
```

| 選び方 | 書き方 |
|--------|-------|
| ちょうど1つ選ぶ | `Σ size == 1` |
| 選ばないか、1つだけ | `Σ size <= 1` |
| 選んだものの値を使う | `Σ 値 × size` |
| A を選ぶなら B も選ぶ | `size_A <= size_B`（第13章 one more thing） |

ハンズオン 14-A で解いた結果です。

```text
■ 基本: Optimal  利益 1,380,000 円（固定費 1,500,000 円）
  釜: 小型釜 0.00 / 中型釜 1.00 / 大型釜 0.00
  生産: ジャム 1,200（run=1.00） / シロップ 0（run=0.00） / ドレッシング 1,500（run=1.00）
  自動ラベラー: 1.00
```

**初花**: 中型釜で、シロップは作らない。ジャムとドレッシングは需要いっぱいまで作って、自動ラベラーも入れる。

**マリゴールド**: 中型釜の能力は2,000。ジャム1,200とドレッシング1,500（0.5倍なので750）で1,950を使う。残りの50ではシロップは最低ロットの200に届かないから、作らないんだ。

**初花**: じゃあ、大型釜にすればシロップも作れるよね。

**マリゴールド**: 大型釜は中型より月100万円高い。シロップ1,000ケースで増える利益は、粗利1,200円からラベル代100円を引いて110万円、そこから段取り費15万円を引くと95万円。100万円には届かないんだ。大型釜が月180万円だったら、どうなるか見てみよう。

```text
■ 大型釜が月180万円なら: Optimal  利益 1,430,000 円（固定費 2,550,000 円）
  釜: 小型釜 0.00 / 中型釜 0.00 / 大型釜 1.00
  生産: ジャム 1,200（run=1.00） / シロップ 1,000（run=1.00） / ドレッシング 1,500（run=1.00）
  自動ラベラー: 1.00
```

**初花**: 大型釜に変わって、シロップも作るようになった！ 固定費は255万円に増えたけど、利益も143万円に増えてる。

**マリゴールド**: 固定費があると、答えが **ある値を境にがらっと変わる** ことがある。連続変数だけのモデルでは、答えは少しずつ変わることが多いけど、バイナリ変数があると、こういう飛び方をするんだ。

## 14.5　Big-M法の考え方と注意点

**マリゴールド**: ここまで何度も出てきた `make <= M × run` の `M`。この書き方を **Big-M法** と呼ぶよ。

**初花**: Mは「十分に大きな数」なんだよね。だったら、100万とか1億とか、とにかく大きい数を入れておけば安心じゃない？

**マリゴールド**: そう考えたくなるよね。でも、大きすぎても小さすぎても困るんだ。三つの M で比べてみよう。

### M が大きすぎる場合

まず、整数の条件を外した緩和問題で比べます（第12章 12.4）。

```text
■ Big-M ＝ 需要（整数の条件を外す）: Optimal  利益 1,504,527 円（固定費 1,430,473 円）
  釜: 小型釜 0.00 / 中型釜 1.00 / 大型釜 0.00
  生産: ジャム 1,200（run=1.00） / シロップ 50（run=0.05） / ドレッシング 1,500（run=1.00）
  自動ラベラー: 0.74
■ Big-M ＝ 100万（整数の条件を外す）: Optimal  利益 2,128,335 円（固定費 1,851,665 円）
  釜: 小型釜 0.00 / 中型釜 0.05 / 大型釜 0.95
  生産: ジャム 1,200（run=0.00） / シロップ 1,000（run=0.00） / ドレッシング 1,500（run=0.00）
  自動ラベラー: 0.00
```

**初花**: M を100万にすると、緩和問題の利益が213万円になってる。本当の答えは138万円なのに。`run` が全部0.00なのに、生産量はいっぱいだよ。

**マリゴールド**: `make <= 1,000,000 × run` なら、`run` を0.0012にするだけで1,200ケース作れてしまう。段取り費はほとんど払わずに済むから、緩和問題の上限がとても甘くなるんだ。

**初花**: 上限が甘いと、第12章の分枝限定法で枝を打ち切れなくなる……ってことは、計算が重くなる？

**マリゴールド**: その通り。この問題は小さいから、整数で解けば M が100万でも同じ答えになる。

```text
■ Big-M ＝ 100万: Optimal  利益 1,380,000 円（固定費 1,500,000 円）
```

でも、大きな問題では、この差が計算時間の差になって表れる。それに、とても大きな数と小さな数が混ざると、ソルバーの小数の計算が不安定になることもあるんだ。

### M が小さすぎる場合

```text
■ Big-M ＝ 800（小さすぎる）: Optimal  利益 570,000 円（固定費 1,350,000 円）
  釜: 小型釜 0.00 / 中型釜 1.00 / 大型釜 0.00
  生産: ジャム 800（run=1.00） / シロップ 800（run=1.00） / ドレッシング 800（run=1.00）
  自動ラベラー: 0.00
```

**初花**: 利益が57万円に下がった！ どの商品も800ケースまでしか作れなくなってる。自動ラベラーも入れてない。

**マリゴールド**: M が実際に必要な量より小さいと、**本当は作れる量を、制約が勝手に削ってしまう**。しかも状態は `Optimal` のまま。第7章で話した、一番見つけにくい種類の間違いだよ。

| M の大きさ | 起きること | 気づきやすさ |
|-----------|----------|-----------|
| 小さすぎる | 実行できるはずの答えが切り捨てられ、間違った答えになる | ✕ `Optimal` のまま |
| ちょうどよい（変数の本当の上限） | 正しく、速く解ける | — |
| 大きすぎる | 答えは正しいが、緩和問題が甘くなり遅くなる。数値が不安定になることも | △ 遅さで気づく |

**初花**: じゃあ、M はどうやって決めればいいの？

**マリゴールド**: **その変数が取りうる本当の最大値** を使う。この章では、生産量の M に需要、自動ラベラーの M に需要の合計を使ったね。データから計算できる、意味のある値にするのがコツだよ。

⚠️ Big-M を使ったモデルでは、M の値をコメントやデータに残しておきます。後でデータ（需要など）が増えたとき、M も一緒に増やさないと、「小さすぎる M」の問題が起きます。この章のコードのように、M をデータから計算するようにしておくと安全です。

## ハンズオン 14-A — 設備の導入費用と生産利益を考慮した生産計画を作る

14.1〜14.4 のモデルです。`big_m` を指定しないときは、M をデータ（需要）から計算します。

`ch14_plant.py`:

```python
import copy
import pulp

# うめ食品の新工場の計画（本書用の架空のデータ）。金額は円、数量はケース、期間は1か月
products = {
    "jam":      {"label": "ジャム",       "margin": 1500, "demand": 1200, "kettle": 1.0},
    "syrup":    {"label": "シロップ",     "margin": 1200, "demand": 1000, "kettle": 1.0},
    "dressing": {"label": "ドレッシング", "margin": 900,  "demand": 1500, "kettle": 0.5},
}
# 釜の大きさの選択肢：固定費（円/月）と能力（釜を使う量/月）
kettles = {
    "small":  {"label": "小型釜", "fixed": 500_000,   "capacity": 1200},
    "medium": {"label": "中型釜", "fixed": 900_000,   "capacity": 2000},
    "large":  {"label": "大型釜", "fixed": 1_900_000, "capacity": 3000},
}
SETUP = 150_000           # 商品を作るなら、月に1回の段取り費
MIN_LOT = 200             # 商品を作るなら、最低200ケース
LABEL_HAND = 400          # 手作業のラベル貼り（円/ケース）
LABEL_AUTO = 100          # 自動ラベラーのラベル貼り（円/ケース）
AUTO_FIXED = 300_000      # 自動ラベラーのリース料（円/月）


def solve_plant(products, kettles, big_m=None, relax=False):
    prob = pulp.LpProblem("plant", pulp.LpMaximize)
    cat = "Continuous" if relax else "Binary"

    make = {p: prob.add_variable(f"make_{p}", lowBound=0, upBound=d["demand"]) for p, d in products.items()}
    run = {p: prob.add_variable(f"run_{p}", lowBound=0, upBound=1, cat=cat) for p in products}       # 作るか
    size = {k: prob.add_variable(f"size_{k}", lowBound=0, upBound=1, cat=cat) for k in kettles}      # どの釜か
    auto = prob.add_variable("auto", lowBound=0, upBound=1, cat=cat)                                 # 自動ラベラーを入れるか
    by_auto = {p: prob.add_variable(f"by_auto_{p}", lowBound=0) for p in products}                   # 自動でラベルを貼る量

    margin = pulp.lpSum(products[p]["margin"] * make[p] for p in products)
    label = pulp.lpSum(LABEL_HAND * (make[p] - by_auto[p]) + LABEL_AUTO * by_auto[p] for p in products)
    fixed = (SETUP * pulp.lpSum(run.values())
             + pulp.lpSum(kettles[k]["fixed"] * size[k] for k in kettles)
             + AUTO_FIXED * auto)
    prob += margin - label - fixed, "profit"

    # 釜はちょうど1つ選ぶ
    prob += pulp.lpSum(size.values()) == 1, "one_kettle"
    # 釜の能力は、選んだ釜の能力まで
    prob += (pulp.lpSum(products[p]["kettle"] * make[p] for p in products)
             <= pulp.lpSum(kettles[k]["capacity"] * size[k] for k in kettles)), "kettle_capacity"

    for p, d in products.items():
        m = d["demand"] if big_m is None else big_m
        prob += make[p] <= m * run[p], f"run_max_{p}"          # 作らないなら 0
        prob += make[p] >= MIN_LOT * run[p], f"run_min_{p}"    # 作るなら最低ロット以上
        prob += by_auto[p] <= make[p], f"by_auto_le_make_{p}"
    m = sum(d["demand"] for d in products.values()) if big_m is None else big_m
    prob += pulp.lpSum(by_auto.values()) <= m * auto, "auto_link"   # 入れないなら自動では貼れない

    stats = prob.solve(pulp.HiGHS(msg=False))
    return {
        "status": stats.status_str,
        "profit": pulp.value(prob.objective),
        "make": {p: make[p].value() for p in products},
        "run": {p: run[p].value() for p in products},
        "size": {k: size[k].value() for k in kettles},
        "auto": auto.value(),
        "fixed": pulp.value(fixed),
    }


def show(title, r, products, kettles):
    print(f"■ {title}: {r['status']}  利益 {r['profit']:,.0f} 円（固定費 {r['fixed']:,.0f} 円）")
    print("  釜: " + " / ".join(f"{kettles[k]['label']} {v:.2f}" for k, v in r["size"].items()))
    print("  生産: " + " / ".join(f"{products[p]['label']} {r['make'][p]:,.0f}（run={r['run'][p]:.2f}）" for p in products))
    print(f"  自動ラベラー: {r['auto']:.2f}")


if __name__ == "__main__":
    show("基本", solve_plant(products, kettles), products, kettles)

    cheaper = copy.deepcopy(kettles)
    cheaper["large"]["fixed"] = 1_800_000
    show("大型釜が月180万円なら", solve_plant(products, cheaper), products, cheaper)
```

⚠️ `make` の `upBound` に需要を入れているので、`make <= 需要 × run` の制約は「作るなら需要まで」の役割も兼ねています。

## 振り返り

**初花**: 固定費は「バイナリ変数 × 金額」。そして「固定費を払わないと使えない」は、`量 <= M × バイナリ変数` でつなぐ。この二つで、条件によって費用が変わる問題が書けた。

**マリゴールド**: 釜の選択のように「選んだものの能力を使う」書き方も、実務でよく使うよ。そして、固定費があると答えが境目でがらっと変わる、というのも大事な感覚だね。

**初花**: Big-M は、大きければいいわけじゃない。小さすぎると黙って間違えるのが一番怖い。

**マリゴールド**: だから M はデータから計算する。次の章では、ここまでのバイナリ変数の技を総動員して、勤務シフトを作ってみよう。

## 初花のメモ帳

- 固定費は「バイナリ変数 × 金額」、使うためにはその設備が必要、は `量 <= M × バイナリ変数` で書く
- 「0か、最低量以上」は `make <= M × run` と `make >= 最低量 × run` の2本。複数から1つは `Σ == 1`
- Big-M は変数が取りうる本当の最大値にする。小さすぎると黙って間違え、大きすぎると遅くなる

## マリゴールドの one more thing

**Big-M を使わない書き方もある。**

PuLP 4 では、変数の上下限を「選んだときだけ有効にする」ような特別な制約を直接書く機能は限られていますが、ソルバーによっては **指示制約**（indicator constraint）という、「バイナリ変数が1のときだけ、この制約を守る」という書き方を直接受け付けるものがあります。Big-M の値を自分で決めなくて済むのが利点です。また、釜の選択のように「いくつかの変数のうち、0でないのは1つだけ」という条件には **SOS**（Special Ordered Sets）という仕組みもあり、PuLP 4 では `prob.add_sos_group` で使えます。どれを使えるかはソルバーによって違うので、第19章のソルバー選びと合わせて調べてみてください。
