# 第12章　整数変数とバイナリ変数

**初花**: 前の章で使ったバイナリ変数、すごく便利だった。0か1だけで「担当する・しない」を表せるなんて。

**マリゴールド**: 第4部は、その0と1の力を使い倒す部だよ。「選ぶ・選ばない」「動かす・止める」「使う・使わない」——世の中の判断の多くは、0と1で表せるんだ。

**初花**: でも、第1章で「整数計画問題は計算が重くなることがある」って言ってたよね。

**マリゴールド**: よく覚えていたね。この章では、変数の型の違いを整理して、数量と採用判断を組み合わせる書き方を学ぶ。最後に、なぜ整数が入ると重くなるのか、ソルバーの中で起きていることを自分の手で再現してみよう。

---

## 12.1　連続変数・整数変数・バイナリ変数

**マリゴールド**: まず、三つの型を並べておこう。

| 型 | `cat` | 取る値 | 例 |
|----|-------|-------|----|
| 連続変数 | `"Continuous"`（省略時） | 小数を含む範囲のすべての値 | 原材料のkg、作業時間、輸送量 |
| 整数変数 | `"Integer"` | 整数だけ | ケース数、人数、トラックの台数 |
| バイナリ変数 | `"Binary"` | 0 か 1 だけ | 採用する・しない、担当する・しない |

**初花**: バイナリ変数って、「0以上1以下の整数変数」と同じ？

**マリゴールド**: その通り。PuLPでも、`cat="Binary"` は内部では上下限0〜1の整数変数として扱われている。ただ、`"Binary"` と書けば「これは判断を表す変数だ」という意図がコードに残るから、使い分けたほうがいいよ。

| どの型を選ぶか | 判断の目安 |
|-------------|----------|
| 連続変数 | 小数でも意味がある、または十分大きくて端数が気にならない |
| 整数変数 | 小数では意味がなく、値が小さくて端数の影響が大きい |
| バイナリ変数 | 「する・しない」の判断そのもの |

⚠️ 1万ケース作る計画なら、9,999.6ケースと10,000ケースの違いはほとんど問題になりません。整数変数は計算を重くするので、**本当に必要なところだけ** に使うのが基本です。

---

## 12.2　なぜ「選ぶ・選ばない」を変数にできるのか

**初花**: 前の章では、「担当する・しない」を変数にした。でも、どうして判断なんていう、数っぽくないものを変数にできるんだろう。

**マリゴールド**: 判断を **数として足し算・掛け算できる形** にしたからだよ。0と1には、三つの便利な性質がある。

| 性質 | 式 | 意味 |
|------|----|------|
| スイッチ | `値 × y` | y=1 なら値が残り、y=0 なら消える |
| 数を数える | `y1 + y2 + ... ` | 選ばれた個数 |
| 条件をつなぐ | `x <= M × y` | y=0 なら x も 0 に縛られる |

**初花**: 一つ目と二つ目は、前の章で使ったね。三つ目は初めて見る。

**マリゴールド**: 三つ目が、この章の主役だよ。「採用しない商品は作れない」のように、**判断と数量をつなぐ** ときに使う。次の節で詳しく見よう。

---

## 12.3　数量と採用判断を組み合わせる

うめ食品では、新しい商品ラインで作る新商品を、6つの候補から選ぶことになりました（本書用の架空のデータです）。

| 候補 | 1ケースの利益 | 1ケースの製造時間 | 需要（1か月） |
|------|-----------:|---------------:|-----------:|
| 梅ゼリー | 1,800円 | 0.50 時間 | 120 |
| 梅こんぶ茶 | 1,200円 | 0.25 時間 | 200 |
| 梅サイダー | 1,500円 | 0.40 時間 | 150 |
| 梅ようかん | 2,500円 | 0.90 時間 | 80 |
| 梅のど飴 | 900円 | 0.15 時間 | 250 |
| 梅だれ | 1,300円 | 0.35 時間 | 100 |

条件は次のとおりです。

- 新商品ラインの稼働時間は、1か月100時間
- 売り場の棚の都合で、採用できるのは **3商品まで**
- 採用した商品は、**最低60ケース** 作る（少なすぎると売り場で目立たない）

**初花**: まず、採用のことは考えずに、利益が最大になる数量だけ求めてみたい。

**マリゴールド**: いいね。比べる基準になるから。

```text
■ 採用の判断なし: Optimal  利益 511,800 円
  梅ゼリー: 1.0 ケース
  梅こんぶ茶: 200.0 ケース
  梅サイダー: 30.0 ケース
  梅のど飴: 250.0 ケース
  ライン 100.0 / 100 時間
```

**初花**: 4商品になってるし、梅ゼリーは1ケースだけ。1ケースのために新商品を出すなんて、ありえないよ。

**マリゴールド**: 「3商品まで」も「最低60ケース」も、まだ書いていないからね。書くには、商品ごとに **採用するかどうか** のバイナリ変数 `adopt` を作って、数量 `make` とつなぐ。

```python
adopt = {p: prob.add_variable(f"adopt_{p}", cat="Binary") for p in candidates}

for p, c in candidates.items():
    prob += make[p] <= c["demand"] * adopt[p], f"link_max_{p}"   # 採用しないなら 0 ケース
    prob += make[p] >= MIN_LOT * adopt[p], f"link_min_{p}"       # 採用するなら最低ロット以上
prob += pulp.lpSum(adopt.values()) <= MAX_ITEMS, "max_items"
```

**初花**: 2本の制約で、`adopt` が0のときと1のときで意味が変わるんだね。

**マリゴールド**: 表にすると分かりやすいよ。

| | `adopt = 0`（採用しない） | `adopt = 1`（採用する） |
|---|------------------------|----------------------|
| `make <= 需要 × adopt` | `make <= 0` → 作れない | `make <= 需要` → 需要まで作れる |
| `make >= 60 × adopt` | `make >= 0` → 何もしない | `make >= 60` → 60ケース以上 |
| 結果 | `make = 0` | `60 <= make <= 需要` |

```text
■ 採用の判断あり（バイナリ）: Optimal  利益 502,200 円
  梅こんぶ茶: 166.0 ケース  adopt=1.00
  梅のど飴: 250.0 ケース  adopt=1.00
  梅だれ: 60.0 ケース  adopt=1.00
  ライン 100.0 / 100 時間
```

**初花**: 3商品になって、どれも60ケース以上。梅サイダーが消えて、代わりに梅だれが最低ロットの60ケースで入ってる。

**マリゴールド**: 梅サイダーを入れるなら60ケース以上作らないといけない。そのために梅こんぶ茶を減らすより、梅だれを60ケース作るほうが得、という判断だね。利益は9,600円下がったけど、これが **実際に実行できる計画** の中での最大なんだ。

⚠️ `make <= 需要 × adopt` の「需要」の部分は、`make` が取りうる最大の値を入れます。この数を **Big-M**（大きなM）と呼びます。大きすぎる数を入れると計算が不安定になることがあります。詳しくは第14章で扱います。

## 12.4　整数制約で結果がどう変わるか

**初花**: `adopt` を0〜1の連続変数にしたら、どうなるの？

**マリゴールド**: やってみよう。`make` も `adopt` も、整数の条件をすべて外して解くよ。

```text
■ 整数の条件をすべて外す: Optimal  利益 511,875 円
  梅こんぶ茶: 200.0 ケース  adopt=1.00
  梅サイダー: 31.2 ケース  adopt=0.21
  梅のど飴: 250.0 ケース  adopt=1.00
  ライン 100.0 / 100 時間
```

**初花**: 梅サイダーを「0.21だけ採用」？ 21%だけ棚に並べる……なんてできないよ。

**マリゴールド**: 連続変数にすると、`make <= 150 × adopt` を満たすために、ちょうど必要な分だけ `adopt` を増やせてしまうんだ。最低ロットの制約も `make >= 60 × 0.21 = 12.5` まで緩んでしまう。

| 解き方 | 利益 | 採用 | 意味 |
|--------|-----:|------|------|
| 整数の条件をすべて外す | 511,875 円 | 梅サイダーを0.21採用 | 実行できない。でも「これより良い答えはない」という上限になる |
| バイナリ | 502,200 円 | 3商品を採用 | 実行できる最適解 |

**初花**: 連続で解いた511,875円は、実行できないけど、バイナリの答えはこれを超えられない、ってことだね。

**マリゴールド**: その通り。整数の条件を外した問題を **緩和問題**（かんわもんだい）と呼ぶよ。緩和問題の答えは、元の問題の答えの **上限**（最小化なら下限）になる。この性質が、次の節で見るソルバーの仕組みの鍵なんだ。

---

## 12.5　整数計画問題で計算が重くなる理由

**マリゴールド**: 第1章の屋台の問題を思い出して。整数の条件を外すと、クッキー1.67個で6,133円だった。ソルバーは、ここからどうやって整数の答えを見つけると思う？

**初花**: 1.67を……切り捨てたら1、切り上げたら2。どっちか分からないから、両方試す？

**マリゴールド**: まさにそれ。**「クッキー ≦ 1」の場合と「クッキー ≧ 2」の場合に分けて**、それぞれ緩和問題を解き、また小数が出たらさらに分ける。これを **分枝限定法**（ぶんしげんていほう）と呼ぶんだ。ハンズオン 12-B で再現したときの記録を見てみよう。

```text
#1 上限 6133.3 (cookie=1.66667, muffin=8, cake=5) → cookie で分ける
  #2 整数解 6000 (cookie=1, muffin=8, cake=5) → 暫定解を更新
  #3 上限 6130.0 (cookie=2, muffin=7.8, cake=5) → muffin で分ける
    #4 上限 6116.7 (cookie=3.33333, muffin=7, cake=5) → cookie で分ける
      #5 整数解 6050 (cookie=3, muffin=7, cake=5) → 暫定解を更新
      #6 上限 6110.0 (cookie=4, muffin=6.6, cake=5) → muffin で分ける
        #7 整数解 6100 (cookie=5, muffin=6, cake=5) → 暫定解を更新
        #8 上限 6100.0 ≦ 暫定 6100.0 → 打ち切り
    #9 上限 6125.0 (cookie=2, muffin=8, cake=4.875) → cake で分ける
      #10 上限 6066.7 ≦ 暫定 6100.0 → 打ち切り
      #11 解なし → 打ち切り

最適解: 6100 円 {'cookie': 5.0, 'muffin': 6.0, 'cake': 5.0} / 調べた問題の数: 11
```

**初花**: 木の枝みたいに分かれていく。#2で6,000円の整数解が見つかって、それが「暫定解」になったんだね。

**マリゴールド**: そして大事なのが **打ち切り**。#10は、緩和問題の上限が6,066.7円で、もう見つかっている6,100円より小さい。その先をどれだけ調べても6,100円を超えられないから、調べるのをやめるんだ。

**初花**: 12.4 の「緩和問題の答えは上限になる」が、ここで効いてるんだ！ 全探索なら594通りだったのに、11個の問題を解いただけで済んでる。

**マリゴールド**: そう。それに、第2章のHiGHSのログを覚えている？ `BestBound` が 6130、`BestSol` が 6000 → 6050 → 6100 と動いていたよね。あれは、この木の上限と暫定解の動きそのものなんだ。

| 分枝限定法の言葉 | 意味 | HiGHSのログ |
|---------------|------|-----------|
| 緩和問題の答え | その枝で達成できる上限 | `BestBound` |
| 暫定解 | これまでに見つかった最良の整数解 | `BestSol` |
| 分枝 | 小数の変数で問題を2つに分ける | `B&B Tree` |
| 限定（打ち切り） | 上限が暫定解以下なら、その枝は調べない | — |
| ギャップ | 上限と暫定解の差 | `Gap` |

**初花**: じゃあ、重くなるのは、打ち切れない枝がたくさん残るときってこと？

**マリゴールド**: その通り。変数が増えると、枝の数は爆発的に増える。上限と暫定解の差がなかなか縮まらない問題では、ソルバーでも時間がかかるんだ。ハンズオン 12-C で、候補の数を増やしながら、連続変数とバイナリ変数で解く時間を比べた結果を見てみよう。

```text
| 候補の数 | 連続（0〜1） | 秒 | バイナリ | 秒 |
|-------:|-----------:|---:|-------:|---:|
| 25 | 913.9 | 0.00 | 894（Optimal） | 0.01 |
| 50 | 1,867.1 | 0.00 | 1,848（Optimal） | 0.16 |
| 100 | 4,037.4 | 0.00 | 4,027（Optimal） | 0.21 |
| 200 | 7,837.3 | 0.00 | 7,823（Optimal） | 2.27 |
| 400 | 15,418.0 | 0.00 | 15,410（Optimal） | 13.17 |
```

**初花**: 連続変数はずっと一瞬なのに、バイナリは候補が倍になるたびに何倍も時間がかかってる。

**マリゴールド**: 秒数はパソコンによって変わるけど、**増え方** はどこでも似たような傾向になる。だから、整数変数は本当に必要なところだけに使い、変数を減らす工夫（作れない組み合わせは変数を作らない、など）が大切になるんだ。時間がかかりすぎるときの対処は、第19章で扱うよ。

| 重さを抑える工夫 | 例 |
|---------------|----|
| 整数変数を必要なところだけにする | 大きな数量は連続変数にする |
| 不要な変数を作らない | 担当できない組み合わせを除く（第9章・第11章） |
| Big-M をできるだけ小さくする | 需要の上限など、意味のある値を使う（第14章） |
| 時間制限を付けて、良い解で止める | 第19章 |

## ハンズオン 12-A — 商品の採用・不採用を含む生産計画を作る

12.3〜12.4 のモデルです。`use_binary` で採用の判断を入れるかどうか、`adopt_cat` で採用の変数を整数にするか連続にするかを切り替えます。

`ch12_adopt.py`:

```python
import pulp

# 新商品の候補（本書用の架空のデータ）。数量はケース、期間は1か月
candidates = {
    "jelly":   {"label": "梅ゼリー",       "profit": 1800, "hours": 0.50, "demand": 120},
    "tea":     {"label": "梅こんぶ茶",     "profit": 1200, "hours": 0.25, "demand": 200},
    "cider":   {"label": "梅サイダー",     "profit": 1500, "hours": 0.40, "demand": 150},
    "yokan":   {"label": "梅ようかん",     "profit": 2500, "hours": 0.90, "demand": 80},
    "candy":   {"label": "梅のど飴",       "profit": 900,  "hours": 0.15, "demand": 250},
    "sauce":   {"label": "梅だれ",         "profit": 1300, "hours": 0.35, "demand": 100},
}
LINE_HOURS = 100   # 新商品用ラインの稼働時間（1か月）
MIN_LOT = 60       # 採用した商品は、最低60ケース作る
MAX_ITEMS = 3      # 採用できるのは3商品まで（売り場の棚の数）


def solve(use_binary=True, adopt_cat="Binary"):
    prob = pulp.LpProblem("new_products", pulp.LpMaximize)

    make_cat = "Integer" if adopt_cat == "Binary" else "Continuous"
    make = {p: prob.add_variable(f"make_{p}", lowBound=0, cat=make_cat) for p in candidates}
    prob += pulp.lpSum(candidates[p]["profit"] * make[p] for p in candidates), "total_profit"
    prob += pulp.lpSum(candidates[p]["hours"] * make[p] for p in candidates) <= LINE_HOURS, "line"

    if use_binary:
        # 1 なら「その商品を採用する」
        if adopt_cat == "Binary":
            adopt = {p: prob.add_variable(f"adopt_{p}", cat="Binary") for p in candidates}
        else:
            adopt = {p: prob.add_variable(f"adopt_{p}", lowBound=0, upBound=1) for p in candidates}
        for p, c in candidates.items():
            prob += make[p] <= c["demand"] * adopt[p], f"link_max_{p}"   # 採用しないなら 0 ケース
            prob += make[p] >= MIN_LOT * adopt[p], f"link_min_{p}"       # 採用するなら最低ロット以上
        prob += pulp.lpSum(adopt.values()) <= MAX_ITEMS, "max_items"
    else:
        adopt = None
        for p, c in candidates.items():
            prob += make[p] <= c["demand"], f"demand_{p}"

    stats = prob.solve(pulp.HiGHS(msg=False))
    return stats, prob, make, adopt


def show(title, stats, prob, make, adopt):
    print(f"■ {title}: {stats.status_str}  利益 {pulp.value(prob.objective):,.0f} 円")
    used = sum(candidates[p]["hours"] * make[p].value() for p in candidates)
    for p, c in candidates.items():
        a = "" if adopt is None else f"  adopt={adopt[p].value():.2f}"
        if make[p].value() > 0.5 or (adopt is not None and adopt[p].value() > 1e-6):
            print(f"  {c['label']}: {make[p].value():.1f} ケース{a}")
    print(f"  ライン {used:.1f} / {LINE_HOURS} 時間")


if __name__ == "__main__":
    show("採用の判断なし", *solve(use_binary=False))
    show("採用の判断あり（バイナリ）", *solve(use_binary=True))
    show("整数の条件をすべて外す", *solve(use_binary=True, adopt_cat="Continuous"))
```

実行すると、12.3 と 12.4 で見た3つの結果が順に表示されます。

## ハンズオン 12-B — 分枝限定法を自分の手で再現する

ソルバーの中で起きていることを、緩和問題を繰り返し解くことで再現します。実務でこのコードを使うことはありませんが、整数計画問題の解き方の考え方がよく分かります。

`ch12_branch.py`:

```python
import math
import pulp

items = {
    "cookie": {"cost": 300, "profit": 200, "max": 10},
    "muffin": {"cost": 500, "profit": 350, "max": 8},
    "cake":   {"cost": 800, "profit": 600, "max": 5},
}
budget = 8500


def solve_relaxed(bounds):
    """整数の条件を外して（連続変数で）解く。bounds は {商品: (下限, 上限)}"""
    prob = pulp.LpProblem("relaxed", pulp.LpMaximize)
    x = {n: prob.add_variable(n, lowBound=bounds[n][0], upBound=bounds[n][1]) for n in items}
    prob += pulp.lpSum(items[n]["profit"] * x[n] for n in items)
    prob += pulp.lpSum(items[n]["cost"] * x[n] for n in items) <= budget
    stats = prob.solve(pulp.HiGHS(msg=False))
    if stats.status_str != "Optimal":
        return None, None
    return pulp.value(prob.objective), {n: x[n].value() for n in items}


best = {"profit": -1, "plan": None}
count = 0


def branch(bounds, depth):
    global count
    count += 1
    profit, x = solve_relaxed(bounds)
    indent = "  " * depth
    if profit is None:
        print(f"{indent}#{count} 解なし → 打ち切り")
        return
    plan = ", ".join(f"{n}={v:g}" for n, v in x.items())
    if profit <= best["profit"] + 1e-9:
        print(f"{indent}#{count} 上限 {profit:.1f} ≦ 暫定 {best['profit']} → 打ち切り")
        return
    frac = [n for n, v in x.items() if abs(v - round(v)) > 1e-6]
    if not frac:
        print(f"{indent}#{count} 整数解 {profit:.0f} ({plan}) → 暫定解を更新")
        best["profit"], best["plan"] = profit, x
        return
    n = frac[0]
    v = x[n]
    print(f"{indent}#{count} 上限 {profit:.1f} ({plan}) → {n} で分ける")
    low, high = bounds[n]
    branch({**bounds, n: (low, math.floor(v))}, depth + 1)   # n ≦ 切り捨て
    branch({**bounds, n: (math.ceil(v), high)}, depth + 1)   # n ≧ 切り上げ


branch({n: (0, items[n]["max"]) for n in items}, 0)
print()
print(f"最適解: {best['profit']:.0f} 円 {best['plan']} / 調べた問題の数: {count}")
```

実行結果は 12.5 の木のとおりです。

| 関数 | 役割 |
|------|------|
| `solve_relaxed` | 上下限を変えた緩和問題を解く |
| `branch` | 小数の変数で2つに分け、自分自身を呼び出す（再帰） |
| `best` | 暫定解（これまでで最良の整数解） |

⚠️ 実際のソルバーは、どの変数で分けるか、どの枝から調べるかを工夫し、さらに「切除平面」などの技術で上限を素早く下げます。このコードは考え方を示すための最小限のものです。

## ハンズオン 12-C — 問題の大きさと計算時間を比べる

ランダムに作った「選ぶ・選ばない」の問題で、候補の数を増やしながら計算時間を測ります。乱数の種（`seed`）を固定しているので、何度実行しても同じ問題になります。

`ch12_scale.py`:

```python
import random
import time
import pulp


def make_data(n, m=5, seed=1):
    """n 個の候補・m 種類の資源をもつ、ランダムな選択問題を作る"""
    rng = random.Random(seed)
    value = [rng.randint(10, 100) for _ in range(n)]
    use = [[rng.randint(5, 50) for _ in range(n)] for _ in range(m)]
    cap = [sum(row) // 2 for row in use]
    return value, use, cap


def solve(n, cat):
    value, use, cap = make_data(n)
    prob = pulp.LpProblem("select", pulp.LpMaximize)
    x = [prob.add_variable(f"x{i}", lowBound=0, upBound=1, cat=cat) for i in range(n)]
    prob += pulp.lpSum(v * xi for v, xi in zip(value, x))
    for k, row in enumerate(use):
        prob += pulp.lpSum(u * xi for u, xi in zip(row, x)) <= cap[k], f"res_{k}"
    start = time.perf_counter()
    stats = prob.solve(pulp.HiGHS(msg=False, timeLimit=60))
    elapsed = time.perf_counter() - start
    return stats.status_str, pulp.value(prob.objective), elapsed


if __name__ == "__main__":
    print("| 候補の数 | 連続（0〜1） | 秒 | バイナリ | 秒 |")
    print("|-------:|-----------:|---:|-------:|---:|")
    for n in [25, 50, 100, 200, 400]:
        s1, v1, t1 = solve(n, "Continuous")
        s2, v2, t2 = solve(n, "Binary")
        print(f"| {n} | {v1:,.1f} | {t1:.2f} | {v2:,.0f}（{s2}） | {t2:.2f} |")
```

`timeLimit=60` は、1問あたり60秒で打ち切る設定です。手元のパソコンが遅い場合でも、400個の問題で止まったままにならないようにしています。秒数は環境によって変わりますが、バイナリ変数のほうだけが急に重くなる傾向を確かめてください。

## 初花のメモ帳

- 型は連続・整数・バイナリの3つ。整数変数は計算を重くするので、必要なところだけに使う
- 数量と採用判断は `make <= 上限 × adopt`（採用しないなら0）と `make >= 最低量 × adopt`（採用するなら最低量以上）でつなぐ
- 整数の条件を外した緩和問題の答えは上限になる。ソルバーはそれを使って分枝限定法で枝を打ち切る

## マリゴールドの one more thing

**緩和問題とのギャップは、モデルの「書き方の良さ」の目安になる。**

同じ問題でも、制約の書き方によって緩和問題の答えが変わります。たとえば `make <= 需要 × adopt` の「需要」を、意味のない大きな数（100万など）にすると、緩和問題では `adopt` をごく小さな値にするだけで済んでしまい、上限が甘くなります。上限が甘いと、分枝限定法で枝を打ち切れず、計算が重くなります。緩和問題の答えと整数の答えの差が小さいモデルほど、速く解けることが多いのです。第14章のBig-M法では、この差を意識した書き方を学びます。
