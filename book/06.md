# 第6章　最適解を正しく読み取る

**初花**: 前の章の最後で言ったこと、ずっと気になってるんだ。ソルバーが「Optimal」って言っても、本当に全部の制約を守れてるのかな。

**マリゴールド**: ソルバー自体はめったに間違えない。間違えるのは、たいてい **モデルを書いた私たちのほう** なんだ。書き忘れた制約はソルバーには見えないからね。

**初花**: じゃあ、どうやって確かめるの？

**マリゴールド**: 答えを取り出して、**ソルバーとは別に自分のコードで検算する**。この章では、結果の読み方、検算のしかた、そして人に見せるレポートの作り方までを通しでやろう。

---

## 6.1　最適化結果と目的関数値

**マリゴールド**: 結果を読むときは、いつも **状態を最初に見る**。状態が `Optimal` でなければ、そのあとの数字は信じてはいけないんだ。

`stats.status_str` が返す主な状態です。

| 状態 | 意味 | 変数の値 |
|------|------|---------|
| `Optimal` | 最適解が見つかった | 使ってよい |
| `Infeasible` | 制約をすべて満たす答えがない | 意味なし |
| `Unbounded` | 目的関数をいくらでも良くできてしまう | 意味なし |
| `NotSolved` | まだ解いていない | `None` |
| `TimeLimit` など | 時間などの制限で途中終了 | 第19章で扱う |

**初花**: 第4章で単位を間違えたとき、`Infeasible` なのに値が0って表示されたよね。

**マリゴールド**: そう、あれが危ないところ。値は入っているように見えても、それは答えではない。だからプログラムでは、状態を確かめて、`Optimal` 以外なら **そこで止める** ようにしよう。

```python
stats = prob.solve(pulp.HiGHS(msg=False))

if stats.status_str != "Optimal":
    raise SystemExit(f"最適解が得られませんでした: {stats.status_str}")
```

目的関数の値は、次のどちらでも取り出せます。

| 書き方 | 値 |
|--------|----|
| `pulp.value(prob.objective)` | 目的関数の値 |
| `stats.objective` | 同じ値（`solve()` の戻り値から） |

## 6.2　各変数の値を取得する

**マリゴールド**: 変数の値は、辞書内包表記で **普通のPythonの辞書** に移しておくと扱いやすい。

```python
solution = {p: var.value() for p, var in make.items()}
print(solution)
```

```text
{'jam': 19.0, 'syrup': 13.000000000000005, 'umeboshi': 13.999999999999995}
```

**初花**: またいた、小さな端数。整数の変数なのに `13.999999999999995` って、ちょっと気持ち悪い。

**マリゴールド**: 整数変数でも、ソルバーの中では小数で計算しているからね。整数変数の値は、**検証が済んだあとで** `round()` で整数に直して使おう。

| 場面 | 使う値 | 理由 |
|------|-------|------|
| 検証するとき | `var.value()` そのまま | 本当に整数になっているかを確かめたい |
| 表示・保存・ほかの計算 | `round(var.value())` | 端数を消して扱いやすくする |

⚠️ 整数変数の値を `int()` で変換してはいけません。`int(13.999999999999995)` は `13` になってしまいます（切り捨て）。`round()` を使います。

## 6.3　制約条件を満たしているか検証する

**初花**: 検算って、具体的には何をするの？

**マリゴールド**: モデルを作るのに使ったのと **同じデータ** を使って、答えが条件を守っているかを普通のPythonで計算し直すんだ。PuLPの式は使わない。そうすれば、モデルの書き間違いにも気づける。

確かめることは、モデル表の各行です。

| 確かめること | 方法 |
|-------------|------|
| 整数になっているか | `abs(x - round(x))` が十分小さいか |
| 下限・上限を守っているか | `products` の `min` / `max` と比べる |
| 資源の上限を守っているか | `resources` の `use` で使用量を計算し、`capacity` と比べる |

`ch06_verify.py`:

```python
import pulp
from ch05_data_model import products, resources, build_model

TOL = 1e-6


def get_solution(make):
    """変数の値を {商品: 数} の普通の辞書にする"""
    return {p: var.value() for p, var in make.items()}


def verify(solution, products, resources):
    """ソルバーの答えを、データだけを使って自分で確かめる"""
    problems = []
    for p, x in solution.items():
        info = products[p]
        if abs(x - round(x)) > TOL:
            problems.append(f"{p}: 整数ではない ({x})")
        if x < info["min"] - TOL:
            problems.append(f"{p}: 下限 {info['min']} を下回る ({x})")
        if info["max"] is not None and x > info["max"] + TOL:
            problems.append(f"{p}: 上限 {info['max']} を超える ({x})")
    for r, info in resources.items():
        used = sum(info["use"].get(p, 0) * x for p, x in solution.items())
        if used > info["capacity"] + TOL:
            problems.append(f"{r}: 上限 {info['capacity']} を超える ({used})")
    return problems


if __name__ == "__main__":
    prob, make, used = build_model(products, resources)
    stats = prob.solve(pulp.HiGHS(msg=False))

    if stats.status_str != "Optimal":
        raise SystemExit(f"最適解が得られませんでした: {stats.status_str}")

    solution = get_solution(make)
    print("解:", solution)

    problems = verify(solution, products, resources)
    print("検証:", "OK" if not problems else problems)

    # わざと間違った案を検証してみる
    bad = {"jam": 20, "syrup": 13, "umeboshi": 14.5}
    print("間違った案の検証:")
    for msg in verify(bad, products, resources):
        print("  -", msg)
```

実行結果:

```text
解: {'jam': 19.0, 'syrup': 13.000000000000005, 'umeboshi': 13.999999999999995}
検証: OK
間違った案の検証:
  - umeboshi: 整数ではない (14.5)
  - ume_g: 上限 18000 を超える (18450.0)
  - work_min: 上限 720 を超える (747.5)
```

**初花**: `TOL` って何？ 「許容誤差」？

**マリゴールド**: そう、tolerance の略。`13.999999999999995` を「整数ではない」と判定しないように、ごく小さなずれは許すんだ。100万分の1（`1e-6`）くらいにしておけば、ふつうの問題では十分だよ。

**初花**: 間違った案のほうは、ちゃんと三つとも見つけてくれた。梅干しの14.5パックと、梅と作業時間のオーバー。

**マリゴールド**: この `verify` は、ソルバーの答えだけでなく、**人が手で作った案** も検査できる。「この案でいける？」と聞かれたときにも使える道具になるよ。

⚠️ 検証関数は、モデルを作る関数 `build_model` とは **別に** 書くことが大切です。同じ式を使い回すと、モデルの書き間違いがそのまま検証にも写り、間違いに気づけません。

## 6.4　最適解が複数ある場合

**初花**: 最適解って、いつも1つに決まるの？

**マリゴールド**: 決まらないこともある。第3章の梅工房で、ジャムの利益が1,000円、シロップが400円に変わったとしよう。

**初花**: 解いてみると……ジャム30kg、シロップ30Lで42,000円。第3章と同じ量だ。

**マリゴールド**: 実はこの条件だと、**ジャム42kg・シロップ0L** でも42,000円になるんだ。その間の量も全部そう。利益の式（1000：400）が作業時間の制約（0.5：0.2）とちょうど同じ比率だから、作業時間を使い切る組み合わせは、どれも同じ利益になる。

| 案 | ジャム | シロップ | 利益 | 梅の使用量 |
|----|-------|---------|------|-----------|
| ソルバーが返した案 | 30 kg | 30 L | 42,000 円 | 33.0 kg |
| 中間の案 | 36 kg | 15 L | 42,000 円 | 29.1 kg |
| ジャムだけの案 | 42 kg | 0 L | 42,000 円 | 25.2 kg |

**初花**: 利益が同じなら、梅が余るジャムだけの案のほうがよくない？ 余った梅で別のものが作れるし。

**マリゴールド**: その「同じなら、こっちがいい」を、**2段階目の目的関数** としてソルバーに伝えればいい。1段目で最大の利益を求めて、2段目では「利益は最大のまま」という制約を足して、梅の使用量を最小にするんだ。

`ch06_multi.py`:

```python
import pulp


def build(sense):
    prob = pulp.LpProblem("ume_kobo", sense)
    jam = prob.add_variable("jam", lowBound=0)
    syrup = prob.add_variable("syrup", lowBound=0)
    exprs = {
        "profit": 1000 * jam + 400 * syrup,   # ジャムの利益が1,000円、シロップが400円
        "ume": 0.6 * jam + 0.5 * syrup,
        "hours": 0.5 * jam + 0.2 * syrup,
    }
    prob += exprs["ume"] <= 33, "ume_kg"
    prob += exprs["hours"] <= 21, "work_hours"
    return prob, jam, syrup, exprs


def show(title, stats, jam, syrup, exprs):
    print(f"[{title}] {stats.status_str}: 利益 {pulp.value(exprs['profit']):,.0f} 円 / "
          f"ジャム {jam.value():.1f} kg / シロップ {syrup.value():.1f} L / 梅 {pulp.value(exprs['ume']):.1f} kg")


# 1段目：利益を最大化
prob, jam, syrup, exprs = build(pulp.LpMaximize)
prob += exprs["profit"], "total_profit"
stats = prob.solve(pulp.HiGHS(msg=False))
show("利益最大", stats, jam, syrup, exprs)
best = pulp.value(exprs["profit"])

# 2段目：利益は最大のまま、梅の使用量を最小化
prob, jam, syrup, exprs = build(pulp.LpMinimize)
prob += exprs["ume"], "ume_used"
prob += exprs["profit"] >= best - 1e-6, "keep_best_profit"
stats = prob.solve(pulp.HiGHS(msg=False))
show("梅を節約", stats, jam, syrup, exprs)

# 2段目（別案）：利益は最大のまま、シロップを最大化
prob, jam, syrup, exprs = build(pulp.LpMaximize)
prob += syrup, "syrup_amount"
prob += exprs["profit"] >= best - 1e-6, "keep_best_profit"
stats = prob.solve(pulp.HiGHS(msg=False))
show("シロップ多め", stats, jam, syrup, exprs)
```

実行結果:

```text
[利益最大] Optimal: 利益 42,000 円 / ジャム 30.0 kg / シロップ 30.0 L / 梅 33.0 kg
[梅を節約] Optimal: 利益 42,000 円 / ジャム 42.0 kg / シロップ 0.0 L / 梅 25.2 kg
[シロップ多め] Optimal: 利益 42,000 円 / ジャム 30.0 kg / シロップ 30.0 L / 梅 33.0 kg
```

**初花**: 利益はどれも42,000円のまま、梅を7.8kgも節約できる案が出てきた。

**マリゴールド**: 最適解が複数あるとき、ソルバーはそのうち **どれか1つ** を返すだけで、どれを返すかは決まっていない。こだわりがあるなら、2段目の目的として明示しよう。

| ポイント | 説明 |
|---------|------|
| 最適解が複数あるサイン | 利益の比率が、効いている制約の係数の比率と同じ |
| ソルバーの返す答え | 複数のうちの1つ。ソルバーやバージョンで変わることがある |
| 好みの案を選ぶ方法 | 1段目の最適値を制約に固定して、2段目の目的関数で選ぶ |
| `best - 1e-6` の理由 | 小数の誤差で「最適値ちょうど」を満たせなくなるのを防ぐ |

## 6.5　最適解と実際に採用すべき案の違い

**初花**: 最適解が出て、検証もOK。じゃあ、あとはその通りに作ればいいよね。

**マリゴールド**: もう一歩だけ考えてほしい。屋台の最適解では、作業時間が720分 **ぴったり** だった。当日、ジャムを煮るのに予定より時間がかかったら？

**初花**: ……全部は作れなくなる。お客さんが来るまでに間に合わないかも。

**マリゴールド**: 最適解は、モデルに書いた条件の中では一番いい。でも現実は、モデルに書いていないことで揺れる。だから実際に採用する案は、**少し余裕を残す** ことが多いんだ。作業時間の1割を余裕として残して、もう一度解いてみよう。

`ch06_buffer.py`（`solve_and_collect` と `print_report` はハンズオン 6-A で作ります）:

```python
import copy
from ch05_data_model import products, resources
from ch06_report import solve_and_collect, print_report

# 作業時間に1割の余裕を残す（720分 → 648分しか計画に使わない）
buffered = copy.deepcopy(resources)
buffered["work_min"]["capacity"] = int(12 * 60 * 0.9)

result = solve_and_collect(products, buffered)
print_report(result, products, buffered)
```

| 案 | ジャム・シロップ・梅干し | 利益 | 作業時間 | 効いている資源 |
|----|------------------------|------|---------|--------------|
| 最適解 | 19・13・14 | 20,750 円 | 720 / 720 分 | 作業時間 |
| 余裕1割の案 | 12・16・16 | 19,800 円 | 640 / 720 分 | 梅 |

**初花**: 利益は950円減るけど、80分も余裕ができる。わたしなら、こっちを選ぶかも。

**マリゴールド**: どちらを選ぶかは、初花が決めることだよ。最適化の役目は、**選択肢とその差を数字で見せる** こと。最終判断を人がするための材料なんだ。

最適解をそのまま採用する前に、次の点を確かめます。

| 確かめること | 例 |
|-------------|----|
| ぴったり使い切った資源に余裕は要らないか | 作業時間・機械の稼働時間 |
| モデルに書いていない条件はないか | 「ジャムは看板商品だから多めに」 |
| データの数字はどのくらい確かか | 利益や需要は見込みの値 |
| 端数を現場で扱えるか | 30.0kg と 29.7kg の違いに意味はあるか |

## ハンズオン 6-A — 結果を集計してレポートを作る

これまでの内容をまとめ、利益・生産数・資源の使用量をレポートにします。結果を1つの辞書にまとめる関数と、Markdownの表として表示する関数に分けます。

`ch06_report.py`:

```python
import pulp
from ch05_data_model import products, resources, build_model
from ch06_verify import verify

TOL = 1e-6


def solve_and_collect(products, resources):
    prob, make, used = build_model(products, resources)
    stats = prob.solve(pulp.HiGHS(msg=False))
    if stats.status_str != "Optimal":
        raise RuntimeError(f"最適解が得られませんでした: {stats.status_str}")

    raw = {p: var.value() for p, var in make.items()}
    problems = verify(raw, products, resources)
    if problems:
        raise RuntimeError(f"検証に失敗しました: {problems}")

    result = {
        "profit": pulp.value(prob.objective),
        "make": {p: round(x) for p, x in raw.items()},   # 整数変数なので丸めて持つ
        "resources": {},
    }
    for r, info in resources.items():
        u = pulp.value(used[r])
        result["resources"][r] = {
            "used": u,
            "capacity": info["capacity"],
            "slack": info["capacity"] - u,
            "rate": u / info["capacity"],
            "binding": info["capacity"] - u < TOL,
        }
    return result


def print_report(result, products, resources):
    print(f"利益合計: {result['profit']:,.0f} 円")
    print()
    print("| 商品 | 数 | 利益 |")
    print("|------|---:|-----:|")
    for p, n in result["make"].items():
        print(f"| {products[p]['label']} | {n} | {products[p]['profit'] * n:,} |")
    print()
    print("| 資源 | 使用量 | 上限 | 余り | 使用率 | 効いている |")
    print("|------|------:|-----:|-----:|------:|:---------:|")
    for r, d in result["resources"].items():
        mark = "★" if d["binding"] else ""
        print(f"| {resources[r]['label']} | {d['used']:,.0f} | {d['capacity']:,} | "
              f"{d['slack']:,.0f} | {d['rate']:.0%} | {mark} |")


if __name__ == "__main__":
    result = solve_and_collect(products, resources)
    print_report(result, products, resources)
```

実行結果:

```text
利益合計: 20,750 円

| 商品 | 数 | 利益 |
|------|---:|-----:|
| ジャム | 19 | 8,550 |
| シロップ | 13 | 5,200 |
| 梅干し | 14 | 7,000 |

| 資源 | 使用量 | 上限 | 余り | 使用率 | 効いている |
|------|------:|-----:|-----:|------:|:---------:|
| 梅(g) | 17,900 | 18,000 | 100 | 99% |  |
| 砂糖(g) | 9,000 | 10,000 | 1,000 | 90% |  |
| 作業(分) | 720 | 720 | 0 | 100% | ★ |
| 瓶(個) | 32 | 50 | 18 | 64% |  |
```

表示はMarkdownの表の形にしてあるので、そのままメモアプリやドキュメントに貼り付けられます。

**初花**: 「余り」と「効いている」の列があると、どこがボトルネックか一目で分かるね。

**マリゴールド**: 余りが0の資源は、もし増やせれば利益が増えるかもしれない場所。余りが大きい資源は、減らしても困らない場所。レポートは、次に何を改善するかを考える地図になるんだ。

| `result` のキー | 中身 |
|----------------|------|
| `profit` | 利益の合計 |
| `make` | 商品ごとの数（整数に丸め済み） |
| `resources` | 資源ごとの使用量・上限・余り・使用率・効いているか |

## 振り返り

**初花**: 状態を見る、値を取り出す、自分で検算する、レポートにする。ソルバーの答えを「読む」だけでも、やることがたくさんあった。

**マリゴールド**: どれも、答えを人に使ってもらうために欠かせない作業だよ。特に検算は、これから問題が大きくなるほど効いてくる。

**初花**: でも今回は、全部ちゃんと解けたからよかった。もし `Infeasible` って出たら、どこが悪いのか探しようがない気がする。

**マリゴールド**: 次の章は、まさにそれ。解けないモデルや、おかしな答えを返すモデルを、順番に直していこう。

## 初花のメモ帳

- 結果はまず状態を見る。`Optimal` 以外なら変数の値は信じずに止める
- 検証は、モデルとは別に、同じデータから普通のPythonで計算し直す
- 最適解が複数あるときは、最適値を固定して2段目の目的で選ぶ。採用案には余裕も考える

## マリゴールドの one more thing

**「効いていない制約」は、消しても答えが変わらない。**

レポートで余りがある制約（たとえば瓶）は、今の答えには影響していません。その制約を外して解き直しても、同じ答えが返ってきます。逆に「効いている」制約を1つだけ外すと、たいていは答えが変わります。この性質は、モデルがおかしな答えを返したときに「どの制約が答えを決めているのか」を探る手がかりになります。次の章のデバッグでは、制約を一つずつ外して原因を絞り込む方法として使います。
