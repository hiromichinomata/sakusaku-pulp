**初花**: マリゴールド、助けて。前の章のコードを見ながら自分で書き直してみたんだけど、状態が `Undefined` って出るんだ。Optimal でも Infeasible でもない、見たことない状態。

**マリゴールド**: いい教材を持ってきたね。コードを見せて。……うん、間違いが **3つ** 隠れている。

**初花**: 3つも！？ 一つずつ見つけ方を教えてほしい。

**マリゴールド**: この章はまさにそのための章だよ。エラーの種類を見分けて、モデルの中身を書き出して、小さく切り分ける。順番に直していこう。

初花が書いたプログラムです。本書用にわざと間違いを残してあります。

`ch07_broken.py`:

```python
import pulp

products = {
    "jam":      {"label": "ジャム", "profit": 450, "min": 10, "max": None},
    "syrup":    {"label": "シロップ", "profit": 400, "min": 0, "max": None},
    "umeboshi": {"label": "梅干し", "profit": 500, "min": 0, "max": 20},
}

resources = {
    "ume_g":    {"label": "梅(g)", "capacity": 18 * 1000,
                 "use": {"jam": 300, "syrup": 400, "umebosi": 500}},
    "sugar_g":  {"label": "砂糖(g)", "capacity": 10 * 1000,
                 "use": {"jam": 200, "syrup": 400}},
    "work_min": {"label": "作業(分)", "capacity": 12 * 60,
                 "use": {"jam": 20, "syrup": 10, "umeboshi": 15}},
    "jars":     {"label": "瓶(個)", "capacity": 5,
                 "use": {"jam": 1, "syrup": 1}},
}


def build_model(products, resources):
    prob = pulp.LpProblem("marche_broken", pulp.LpMaximize)
    make = {
        p: prob.add_variable(f"make_{p}", lowBound=info["min"], upBound=info["max"], cat="Integer")
        for p, info in products.items()
    }
    prob += pulp.lpSum(products[p]["profit"] * make[p] for p in products), "total_profit"
    for r, info in resources.items():
        used = pulp.lpSum(info["use"].get(p, 0) * make[p] for p in products)
        prob += used >= info["capacity"], f"cap_{r}"
    return prob, make


if __name__ == "__main__":
    prob, make = build_model(products, resources)
    stats = prob.solve(pulp.HiGHS(msg=False))
    print("状態:", stats.status_str)
    if stats.status_str == "Optimal":
        print(f"利益: {pulp.value(prob.objective):,.0f} 円")
        print({p: round(v.value()) for p, v in make.items()})
```

実行結果:

```text
状態: Undefined
```

## 7.1　実行エラーとモデリングミス

**マリゴールド**: 最初に、間違いを二つの種類に分けよう。**Pythonが止まる間違い** と、**止まらずに変な答えを出す間違い** だ。

| 種類 | 症状 | 見つけやすさ |
|------|------|------------|
| 実行エラー | `TypeError` などで途中で止まる | ◎ エラーメッセージが場所を教えてくれる |
| モデリングミス（解けない） | `Infeasible` / `Unbounded` / `Undefined` | ○ 状態で気づける |
| モデリングミス（解ける） | `Optimal` なのに答えがおかしい | △ 自分で疑わないと気づけない |

**初花**: 一番怖いのは、最後のやつだね。Optimal って言われたら信じちゃう。

**マリゴールド**: そう。だから第6章の検証が大事なんだ。まず、実行エラーの代表例を見ておこう。どれも **線形でない式** を書こうとしたときに出る。

| 書いたコード | エラー | 原因 |
|-------------|-------|------|
| `x * y` | `TypeError: Non-constant expressions cannot be multiplied` | 変数どうしの掛け算（第1章 1.3） |
| `x ** 2` | `TypeError: unsupported operand type(s) for ** or pow()` | 二乗 |
| `1 / x` | `TypeError: unsupported operand type(s) for /` | 変数で割る |
| `max(x, y)` | `TypeError: '>' not supported between instances of 'LpVariable' and 'LpVariable'` | Pythonの `max` は使えない |
| `x < 3` | `TypeError: '<' not supported ...` | `<` ではなく `<=` を使う |

**初花**: `x / 2` は大丈夫なの？

**マリゴールド**: 数で割るのは `0.5 * x` と同じだから大丈夫。割る相手が **変数** のときだけダメなんだ。

⚠️ PuLPの制約条件には `<`、`>` は使えません。`<=`、`>=`、`==` の3つだけです。

## 7.2　制約条件が矛盾している場合

**初花**: 「制約が矛盾してる」って、どういう状態？

**マリゴールド**: 全部の制約を同時に満たす答えが **一つもない** 状態。たとえば「ジャムは10瓶以上」と「瓶は5個まで」が両方あったら、どうやっても無理だよね。そのとき状態は `Infeasible` になる。

| よくある原因 | 例 |
|-------------|----|
| 上限と下限がぶつかる | 予約10瓶 と 瓶5個 |
| 単位の取り違え | 作業 720分 のつもりが 12（第4章） |
| 等式が厳しすぎる | 「ちょうど18kg使う」（第4章） |
| データの打ち間違い | 50 のつもりが 5 |
| 符号の向き | `<=` のつもりが `>=` |

**初花**: 制約がたくさんあったら、どれとどれがぶつかってるか分からないよね。

**マリゴールド**: 第6章の one more thing を思い出して。**制約を1本ずつ外して解き直す** んだ。外したら解けるようになった制約が、矛盾に関わっている。`build_model` がデータから制約を作る形になっていれば、データから1つ抜くだけで試せるよ。

```python
for skip in resources:
    subset = {r: info for r, info in resources.items() if r != skip}
    prob, make = build_model(products, subset)
    stats = prob.solve(pulp.HiGHS(msg=False))
    print(f"{skip:<9} を外すと → {stats.status_str}")
```

この方法は、ハンズオン 7-A で実際に使います。

## 7.3　目的関数が際限なく改善する場合

**マリゴールド**: 反対に、**いくらでも良くできてしまう** 状態もある。利益を最大化したいのに、作る量の上限がどこにもなければ、利益は無限に増やせてしまうよね。これが `Unbounded`（非有界）だ。

**初花**: 現実には無限に儲かるなんてありえないから、どこかの制約が抜けてるってこと？

**マリゴールド**: その通り。`Unbounded` は、ほぼ間違いなく **制約の書き忘れか、向きの間違い** を意味しているんだ。

| よくある原因 | 例 |
|-------------|----|
| 資源の制約の向きが逆 | `used >= capacity` |
| 変数の下限の書き忘れ | `lowBound` なしで、マイナスの量が許される |
| 最大化と最小化の取り違え | 費用を `LpMaximize` |
| 制約を追加し忘れた | `prob +=` の行が抜けている |

整数変数を含むモデルでは、HiGHSは「解けない」のか「際限がない」のかを見分けられないとき、`Undefined` を返します。ログ（`msg=True`）では次のように表示されます。

```text
Presolve: Primal infeasible or unbounded
...
Solving report
  Status            Primal infeasible or unbounded
```

**初花**: 「解けないか、際限がないか、どっちか」ってこと？ ずいぶん曖昧な返事……。

**マリゴールド**: 整数の問題は難しいから、そう答えるしかない場合があるんだ。見分けたいときは、**整数の指定を外して** 解き直すといい。連続変数の問題なら、ソルバーははっきり答えてくれるよ。

| `cat` | 制約の向き `>=`（間違い） | 制約の向き `<=`（瓶5個のまま） |
|-------|-----------------------|---------------------------|
| `"Integer"` | `Undefined` | `Infeasible` |
| `"Continuous"` | `Unbounded` | `Infeasible` |

## 7.4　変数の定義漏れ・符号ミス

**マリゴールド**: 一番やっかいなのは、エラーも出ず、状態も `Optimal` なのに、答えがおかしいケースだ。代表的なものを挙げておくよ。

| ミス | 何が起きるか |
|------|------------|
| 辞書のキーの打ち間違い（`"umebosi"`） | `get(p, 0)` が0を返し、その商品が資源を使わない扱いになる |
| 係数の符号ミス（`-300` と書いた） | 資源を使うどころか増やす扱いになる |
| 変数を式に入れ忘れた | その商品が資源を使わない扱いになる |
| `0 <= x <= 5` と書いた | `x <= 5` だけが制約になり、`0 <=` は無視される |
| `if x >= 3:` と書いた | 条件は常に真として扱われ、エラーにならない |

**初花**: 最後の二つ、ほんとにエラーにならないの？

**マリゴールド**: ならないんだ。PuLPの比較式はPythonの `if` や連鎖比較の中では正しく働かないのに、黙って通ってしまう。

```python
prob += 0 <= x <= 5, "x_range"   # x <= 5 だけが入る
print(prob.get_constraint_by_name("x_range"))
```

```text
x <= 5
```

| やりたいこと | 正しい書き方 |
|-------------|-------------|
| 0以上5以下 | `add_variable(..., lowBound=0, upBound=5)` か、制約を2本に分ける |
| 「もし x が3以上なら」 | Pythonの `if` では書けない。0/1変数を使う（第14章） |

⚠️ 変数の値で処理を分ける `if` は、解いた **後** の `x.value()` に対してだけ使えます。モデルを作る段階では使えません。

## 7.5　LPファイルを出力してモデルを確認する

**初花**: `print(prob)` でモデルの中身が見られるのは知ってる。ほかの方法もあるの？

**マリゴールド**: `writeLP` で **LPファイル** に書き出せる。LP形式は多くのソルバーが読める標準的な書式で、ファイルに残せば、ほかの人に見せたり、昨日のモデルと見比べたりできるよ。

```python
prob, make = build_model(products, resources)
prob.writeLP("broken.lp")
```

`broken.lp`:

```text
\* marche_broken *\
Maximize
total_profit: 450 make_jam + 400 make_syrup + 500 make_umeboshi
Subject To
cap_jars: make_jam + make_syrup >= 5
cap_sugar_g: 200 make_jam + 400 make_syrup >= 10000
cap_ume_g: 300 make_jam + 400 make_syrup >= 18000
cap_work_min: 20 make_jam + 10 make_syrup + 15 make_umeboshi >= 720
Bounds
 10 <= make_jam
 0 <= make_syrup
 0 <= make_umeboshi <= 20
Generals
make_jam
make_syrup
make_umeboshi
End
```

| LPファイルの部分 | 意味 |
|----------------|------|
| `Maximize` / `Minimize` | 目的関数 |
| `Subject To` | 制約条件（名前: 式） |
| `Bounds` | 変数の上下限 |
| `Generals` | 整数変数の一覧（バイナリは `Binaries`） |

**初花**: あっ、制約が全部 `>=` になってる！ 「上限」なのに「以上」って書いちゃってた。

**マリゴールド**: 一つ目、発見だね。もう一つ、LPファイルから見つかる間違いがあるよ。梅の制約の行をよく見て。

**初花**: `cap_ume_g: 300 make_jam + 400 make_syrup >= 18000`……梅干しがいない！ 梅干しも梅を500g使うはずなのに。

**マリゴールド**: 二つ目も見つかった。LPファイルは、自分が **書いたつもりのモデル** ではなく、**実際にできたモデル** を見せてくれる。表と1行ずつ見比べるのが、いちばん確実なデバッグなんだ。

⚠️ LPファイルの制約は、名前の順に並び替えられることがあります。書いた順番と違っていても気にしなくて大丈夫です。

## 7.6　小さなテストケースで原因を切り分ける

**初花**: でも、商品が100個あったら、LPファイルを全部読むのは無理だよね。

**マリゴールド**: だから、**手で答えが分かるくらい小さなデータ** で試すんだ。第1章で話した、全探索との答え合わせだよ。

`ch07_small_test.py`:

```python
import itertools
import pulp
from ch07_fixed import build_model

# 手で確かめられるくらい小さなデータ
small_products = {
    "a": {"label": "A", "profit": 3, "min": 0, "max": 4},
    "b": {"label": "B", "profit": 5, "min": 1, "max": 3},
}
small_resources = {
    "r1": {"label": "資源1", "capacity": 10, "use": {"a": 2, "b": 3}},
    "r2": {"label": "資源2", "capacity": 6, "use": {"a": 1, "b": 2}},
}


def brute_force(products, resources):
    names = list(products)
    ranges = [range(products[p]["min"], products[p]["max"] + 1) for p in names]
    best = None
    for counts in itertools.product(*ranges):
        x = dict(zip(names, counts))
        if all(sum(info["use"].get(p, 0) * x[p] for p in names) <= info["capacity"]
               for info in resources.values()):
            profit = sum(products[p]["profit"] * x[p] for p in names)
            if best is None or profit > best:
                best = profit
    return best


prob, make = build_model(small_products, small_resources)
stats = prob.solve(pulp.HiGHS(msg=False))
pulp_best = pulp.value(prob.objective)
bf_best = brute_force(small_products, small_resources)

print("PuLP:", stats.status_str, pulp_best)
print("全探索:", bf_best)
print("一致" if stats.status_str == "Optimal" and abs(pulp_best - bf_best) < 1e-6 else "不一致！")
```

修正前の `build_model`（`ch07_broken` から import）で実行した結果:

```text
PuLP: Optimal 27.0
全探索: 16
不一致！
```

修正後の `build_model`（`ch07_fixed` から import）で実行した結果:

```text
PuLP: Optimal 16.0
全探索: 16
一致
```

**初花**: 修正前は、小さなデータだと上限があるから Optimal になっちゃうんだ。でも全探索と比べたら、ちゃんとおかしいって分かる。

**マリゴールド**: 小さなデータは、答えを手で確かめられるのが強みだよ。`build_model` のような **モデルを作る関数** を、データを変えて何度も試せる形にしておくと、こういうテストがすぐ書ける。第20章では、これを自動テストにする。

| 切り分けの方法 | 何が分かるか |
|--------------|------------|
| 制約を1本ずつ外す | 矛盾に関わっている制約 |
| 整数の指定を外す | `Undefined` が解けないのか際限がないのか |
| 小さなデータで全探索と比べる | モデルを作るコードの間違い |
| LPファイルを表と見比べる | 係数・符号・書き忘れ |

### ステップ3：Optimal だけど本当に正しい？

**初花**: 解けた！ ……でも、第4章の答えは20,750円だったよね。同じデータのはずなのに、利益が増えてる。

**マリゴールド**: 同じ条件なのに前より儲かるのは、どこかの制約が **緩くなっている** サインだよ。LPファイルで見つけた梅干しの件を思い出して。

データのキーの書き間違いは、モデルを作る前にデータを検査すると見つけられます。

`ch07_check_data.py`:

```python
from ch07_fixed import products, resources


def check_data(products, resources):
    """データの書き間違いを探す（モデルを作る前に実行する）"""
    problems = []
    for r, info in resources.items():
        for p in info["use"]:
            if p not in products:
                problems.append(f"{r}: 商品 '{p}' は products にない")
        if info["capacity"] < 0:
            problems.append(f"{r}: 上限がマイナス ({info['capacity']})")
    for p, info in products.items():
        if info["max"] is not None and info["min"] > info["max"]:
            problems.append(f"{p}: 下限 {info['min']} が上限 {info['max']} より大きい")
        if not any(p in info["use"] for info in resources.values()):
            problems.append(f"{p}: どの資源も使っていない")
    return problems


for msg in check_data(products, resources):
    print("-", msg)
```

修正前のデータで実行した結果:

**マリゴールド**: 第6章の `verify` も同じデータを使うから、この間違いは見逃してしまう。**データそのものを検査する** 関数が別に必要なんだ。キーを `"umeboshi"` に直して、最後にもう一度実行しよう。

## 初花のメモ帳

- `Infeasible` は制約の矛盾、`Unbounded` は制約の書き忘れや向きの間違い。`Undefined` は整数の指定を外して見分ける
- `writeLP` で書き出したLPファイルを、モデル表と1行ずつ見比べる
- 前より利益が増えたら疑う。データのキーは、モデルを作る前に検査する

## マリゴールドの one more thing

**解けないモデルを「どこまでなら守れるか」に変える。**

制約を1本ずつ外す方法は、制約が多いと時間がかかります。別の方法として、各制約に「はみ出してもよい量」を表す変数を足し、そのはみ出しの合計を最小化する、というやり方があります。たとえば瓶の制約を `jam + syrup <= 50 + over_jars` とし、`over_jars` を0以上の変数にして目的関数で小さくするのです。解くと、どの制約をどれだけ破れば答えがあるのかが分かります。この「はみ出しを許して罰を与える」考え方は、第10章で供給不足を扱うときや、第15章で希望シフトを扱うときにも使います。
